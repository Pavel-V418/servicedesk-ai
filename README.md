# ServiceDeskAI

## Команда

- Вильдеманов Павел — классификатор вида запроса, интеграция пайплайна
- Айвазян Арман — маршрутизатор по линиям поддержки

Объединённый проект хакатона: классификация обращения → маршрутизация по линии → похожие обращения (RAG) → риск SLA → ответ оператору.

```
ServiceDeskAI/
├── main.py                 # точка входа: train / demo / "текст обращения"
├── pipeline.py             # граф LangGraph: связывает все блоки
├── finalizer.py            # итог для оператора: GigaChat (потоком) или шаблон
├── ui/app.py               # веб-интерфейс оператора (Streamlit): анализ обращения + SLA-аналитика
├── config.py               # общие пути (RAG, LLM)
├── requirements.txt
├── classifier/             # ← классификатор вида запроса (Павел)
│   ├── config.py           #   параметры и пути классификатора
│   ├── data_preparation.py #   smart_clean, топ-15, дедупликация
│   ├── model.py            #   обучение: LogReg (вариант B) + CatBoost, порог, вес ансамбля
│   ├── predictor.py        #   инференс: TicketClassifier (вынесен из agent.py)
│   ├── dataset/            #   Обращения_1931.xlsx (+ cleaned_data.csv и бандлы после train)
│   └── tests/              #   test_frozen_set, error_analysis, run_variant_b
├── routing/                # ← маршрутизатор L1/L2/L3 (routing-agent)
│   ├── router.py           #   адаптер TicketRouter для пайплайна
│   └── routing_agent/      #   исходный репозиторий коллеги (src/, models/, reports/)
├── RagAgent/               # ← RAG: похожие обращения (ChromaDB)
│   ├── rag_data_prep.py    #   load_rag_data(): колонки + фильтр пустых описаний
│   ├── rag_build_db.py     #   clean_ticket_text(), build_db() → RagAgent/chroma_db
│   └── rag_search.py       #   TicketRetriever.search_similar()
├── sla/                    # ← SLA
│   ├── sla_analytics.py    #   SLAAnalyzer: статистика для дашборда (коллега)
│   └── risk.py             #   SLARiskEstimator: риск просрочки нового обращения (узел пайплайна)
├── tests/                  # тесты пайплайна: demo, tests_integration (RAG), test_sla
└── tools/check_gigachat.py # проверка ключа GigaChat и замер времени итога
```

## Запуск (из корня ServiceDeskAI)

```bash
pip install -r requirements.txt
python main.py train          # классификатор, маршрутизатор и база RAG (chroma_db)
python main.py train --only rag   # пересобрать только базу RAG
python main.py ui             # веб-интерфейс (то же, что streamlit run ui/app.py)
python main.py demo           # четыре тестовых обращения через весь пайплайн
python main.py sla-dashboard  # SLA-статистика по истории (JSON для дашборда)
python main.py "Всё зависает" --priority Наивысший
python main.py "Не приходит смс с кодом" --service "Портал pochta.ru"
python classifier/tests/test_frozen_set.py   # регрессия классификатора на замороженном тесте
```

### GigaChat (итог для оператора)

Скопируй `.env.example` в `.env` в корне проекта и впиши ключ авторизации в `GIGACHAT_CREDENTIALS`. Файл `.env` в git не попадает. Проверить ключ и замерить время ответа:

```bash
python tools/check_gigachat.py --show --bench 5
```

Без ключа всё работает, только итог собирается по шаблону. В интерфейсе это подписано, а в статусе компонентов видно `llm: шаблон`.

Модели не хранятся в репозитории: joblib, сохранённый одной версией scikit-learn, не открывается в другой. Поэтому после клонирования или обновления библиотек нужно выполнить `python main.py train`.

## Как связаны блоки

| Узел графа | Блок | Что делает |
|---|---|---|
| `classify` | `classifier.TicketClassifier` | smart_clean → ансамбль → вид запроса, уверенность, топ-3, ключевые слова |
| `route` | `routing.TicketRouter` | линия L1/L2/L3 + статус `high/medium_confidence` / `manual_review` |
| `similar_tickets` | `RagAgent.TicketRetriever` | до 3 похожих обращений из ChromaDB |
| `sla` | `sla.SLARiskEstimator` | риск просрочки (низкий / средний / высокий) и типичное время решения |
| `synthesize` | `finalizer.py` | итоговый текст оператору: GigaChat, при недоступности — шаблон |

**Вид запроса для маршрутизатора.** Маршрутизатор обучен с признаком «Вид запроса». У нового обращения этого поля ещё нет, поэтому в него подставляется ответ классификатора. Если оператор ввёл вид запроса сам (`request_kind=...`), используется его значение. Источник значения записывается в `request_kind_source`.

**Риск SLA.** В выгрузке 25 просрочек на 1930 обращений, и 24 из них с приоритетом «(1) Наивысший». Обучать модель на 25 примерах бессмысленно, поэтому риск считается как историческая доля просрочек среди похожих обращений. Сравниваются три признака: приоритет вместе с линией (линию выдаёт маршрутизатор), только приоритет, если в связке приоритет+линия меньше 15 обращений, и вид запроса (его выдаёт классификатор). Из этих долей берётся максимальная. Уровни: 10% и выше — высокий, от 3% — средний, ниже — низкий. Средняя доля просрочек по выгрузке 1.2%. Если маршрутизатор отправил обращение на ручной разбор, в расчёт идёт наиболее вероятная линия. Фактическая длительность и флаг просрочки нужны только для подсчёта этих долей по истории; признаками нового обращения они не служат.

**Итог для оператора (`finalizer.py`).** GigaChat получает текст обращения и результаты всех блоков и пересказывает их по фиксированной структуре: суть, вид запроса, куда направить, риск SLA, похожие случаи, что проверить. В системном промпте прописаны правила: использовать только переданные факты, не менять выводы моделей, не выдавать статус закрытия похожих обращений за решение, прямо говорить о низкой уверенности. Температура 0.2, до ~150 слов, тайм-аут 15 с. Если GigaChat недоступен или не ответил, итог собирается по шаблону. В интерфейсе карточки появляются сразу (`pipeline.analyze_ticket` работает без итога), а итог выводится потоком по мере генерации. Текст обращения при этом уходит во внешний сервис GigaChat.

Если блок не загрузился (нет модели, не установлен пакет), его узел пропускается, а причина выводится при старте (`pipeline.COMPONENT_STATUS`).

## Что изменено при объединении

- `agent.py` разделён на две части. Инференс классификатора вынесен в `classifier/predictor.py`, граф — в `pipeline.py`. Логика классификатора не менялась: на замороженном тесте `predictor` воспроизводит `model.py` без отличий.
- В `classifier/*` импорты теперь вида `from classifier import config`. Пути строятся от папки `classifier/`. RAG-настройки перенесены в корневой `config.py`.
- В тесте `test_frozen_set.py` и в `error_analysis.py` вместо полного графа используется `TicketClassifier`. Это тот же узел `classify`, но без RAG и маршрутизации, поэтому тесты идут быстрее. Скрипты `demo.py` и `tests_integration.py` проверяют RAG и перенесены в корневую папку `tests/`.
- В routing-agent:
  - захардкоженный путь `/Users/armancho/...` заменён на `src/paths.py`. Датасет общий: `classifier/dataset/`;
  - `train_router.py` сохраняет модель в `models/`;
  - `LogisticRegression(solver="liblinear")` на трёх классах падает в scikit-learn ≥ 1.8. В `src/models/weighted_ovr.py` та же схема One-vs-Rest с весами классов реализована явно. После переобучения метрики на финальном временном тесте совпадают с `reports/final_evaluation.txt`: accuracy 0.6891, macro-F1 0.3991;
  - удалены дубликаты: `src/routing/` (не использовался, а `predict.py` вызывал несуществующий `route()`) и копии joblib в `src/models/`.
- В RAG:
  - построение базы в `rag_build_db.py` раньше выполнялось на уровне модуля. `pipeline.py` импортирует оттуда `clean_ticket_text`, поэтому каждый запуск пайплайна пересоздавал базу. Теперь базу строит функция `build_db()`, и запускается она только явно;
  - пути к Excel и `chroma_db` берутся из корневого `config.py`. База строится из той же выгрузки `classifier/dataset/Обращения_1931.xlsx`;
  - на Windows ChromaDB не открывает индекс HNSW, если в пути к базе есть кириллица (`C:\Users\Павел\...` → «Error loading hnsw index»). В таком случае база автоматически кладётся в `C:\Users\Public\ServiceDeskAI\chroma_db`. Свой путь можно задать переменной окружения `CHROMA_DB_PATH`;
  - в `tests/demo.py` и `tests/tests_integration.py` вместо копии кода построения базы вызывается `build_db()`;
  - логика поиска в `rag_search.py` не менялась: порог 0.45, пропуск тикетов 4-й линии, top-3.
- В SLA:
  - в `sla_analytics.py` изменены только пути: файл по умолчанию берётся из `config.SLA_XLSX_PATH`, а не из текущей папки. Логика не менялась;
  - добавлен `sla/risk.py` — оценка риска для одного обращения на основе данных `SLAAnalyzer`, и `tests/test_sla.py`.
- UI:
  - интерфейс routing-agent перенесён из `routing/routing_agent/ui/` в `ui/app.py` и подключён ко всему пайплайну. Вкладка «Анализ обращения» показывает вид запроса, линию, риск SLA, похожие обращения и итог. Вкладка «SLA-аналитика» — это дашборд `SLAAnalyzer`;
  - в форме только то, что оператор знает при регистрации: описание, услуга, компонент, тип запроса и необязательный приоритет. Вид запроса определяет классификатор. Пользователь, часовой пояс, класс обслуживания, критичность и срочность убраны: на финальном временном тесте маршрутизатор без них даёт ту же accuracy 0.689 (macro-F1 0.418 против 0.399). Приоритет оставлен ради оценки риска SLA;
  - поля формы — выпадающие списки со значениями из выгрузки. Раньше приоритет уходил в модель как «Средний» вместо «(3) Средний», модель такое значение не узнавала и молча игнорировала. Появился приоритет «Наивысший»;
  - похожие обращения показываются свёрнутыми (`st.expander`): в заголовке номер, вид, линия и степень близости, при раскрытии — полный текст. Полный оригинальный текст сохраняется в метаданные при построении базы (`rag_build_db.py`), а `rag_search.py` отдаёт его в поле `text`;
  - в `routing/router.py` добавлено приведение приоритета к формату выгрузки («Средний» → «(3) Средний») для вызовов из CLI.
